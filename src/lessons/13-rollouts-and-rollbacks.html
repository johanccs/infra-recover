Rollouts and Rollbacks

Releasing a new version without downtime, and getting back quickly when the new version is bad, is the main reason teams adopt Deployments. This lesson shows what happens during a rollout, how to read a stuck one, and how to undo it.

⏱ 40 min
🎯 Goal of this lesson

Understand the rolling update, follow it with kubectl rollout, and recover from a release that never becomes ready.

Why it matters: a failed release at five in the afternoon is the classic moment of pressure. If you know that a stuck rollout is safe, and that one command returns to the previous version, you can act calmly.

By the end of this lesson you will be able to

  • Describe how a rolling update replaces pods step by step.
  • Explain maxSurge and maxUnavailable.
  • Follow, inspect and undo a rollout.
  • Explain why a failed rollout usually causes no outage.
  • Diagnose ImagePullBackOff during a release.
Words used in this lesson
Rollout
The process of replacing the pods of a Deployment with a new version.
Rolling update
The default rollout strategy: start a few new pods, wait until they are ready, remove a few old ones, and repeat. The app stays available throughout.
Revision
A numbered version of a Deployment's pod template. Each change to the template creates a new one.
`maxSurge` and `maxUnavailable`
The two limits of a rolling update: how many extra pods may exist, and how many may be missing, at any moment.
Rollback
Going back to an earlier revision, with `kubectl rollout undo`.

The situation

Three replicas of the front end serve customers. Version 1.1 is ready to ship. Tomorrow there will be a 1.2, and that one will have a bug nobody caught in testing.

What triggers a rollout

A rollout starts whenever the pod template of a Deployment changes: the image, an environment variable, a resource limit, a label. Changing only replicas is scaling, not a rollout.

```bash kubectl set image deployment/web web=shop/web:1.1 # quick; or edit the file and apply kubectl rollout status deployment/web ``` ```plaintext Waiting for deployment "web" rollout to finish: 1 out of 3 new replicas have been updated... Waiting for deployment "web" rollout to finish: 2 out of 3 new replicas have been updated... Waiting for deployment "web" rollout to finish: 1 old replicas are pending termination... deployment "web" successfully rolled out ```

How a rolling update works

The Deployment creates a new ReplicaSet for the new template and shifts pods from the old ReplicaSet to the new one in small steps:

```plaintext label="3 replicas, default settings" old RS: ●●● new RS: start old RS: ●●● new RS: ○ one extra pod is started (surge) old RS: ●● new RS: ● the new pod is Ready → one old pod is removed old RS: ●● new RS: ●○ next new pod starts ... old RS: new RS: ●●● done; the old ReplicaSet stays, scaled to 0 ```
SettingMeaningDefault
maxSurgeHow many pods above the desired count may exist during the update.25% (rounded up)
maxUnavailableHow many pods below the desired count may be unavailable.25% (rounded down)

With three replicas that means: at most one extra pod, and never fewer than three available. The decisive rule is that an old pod is only removed after a new pod has become Ready.

Watch that rule at work. At every step, count the pods that are receiving traffic:

A stuck rollout is a safe rollout If the new version cannot start (bad image tag, crash at startup, failing readiness probe), its first pod never becomes Ready, so no old pod is removed. The release hangs, the old version keeps serving, and customers notice nothing. This protection depends on a meaningful readiness probe (Lesson 14): without one, a pod counts as ready the moment its process starts.

History and rollback

Old ReplicaSets are kept (ten by default) precisely so that you can go back.

```bash kubectl rollout history deployment/web kubectl rollout history deployment/web --revision=2 # what that revision's pod template was kubectl rollout undo deployment/web # back to the previous revision kubectl rollout undo deployment/web --to-revision=1 ``` ```plaintext deployment.apps/web REVISION CHANGE-CAUSE 1 2 ```

undo does not build or pull anything new: it sets the Deployment's pod template back to that of an earlier ReplicaSet, and a normal rolling update towards the old version follows. The old revision is re-issued under a new number, so after undoing revision 3 the history lists 1, 3 and 4: what used to be revision 2 is now revision 4.

❌ Under pressure

Deleting the failing pods, editing things live, or scaling the Deployment down and up. The broken template is still there, so the same pods come straight back.

✅ What works

kubectl rollout undo, confirm with rollout status, and then find the cause from the failed pod's events and logs without time pressure.

Reading a stuck rollout

```plaintext label="kubectl get deployment web; kubectl get pods" NAME READY UP-TO-DATE AVAILABLE AGE web 3/3 1 3 12m NAME READY STATUS RESTARTS AGE web-c6g9q7brjz-dwx29 1/1 Running 0 12m web-c6g9q7brjz-mvjrq 1/1 Running 0 12m web-c6g9q7brjz-vvxfp 1/1 Running 0 12m web-rhrcvrmcl2-pb8kr 0/1 ImagePullBackOff 0 90s ```
ColumnMeaning here
READY 3/3Three pods are ready (the old ones). Customers are fine.
UP-TO-DATE 1Only one pod has the new template.
Two different hashes in the pod namesTwo ReplicaSets are active: a rollout is in progress.

The new pod's status tells you what kind of failure it is. ImagePullBackOff is the most frequent one during releases:

```plaintext label="kubectl describe pod web-rhrcvrmcl2-pb8kr (events)" Normal Pulling 8s (x2 over 20s) kubelet Pulling image "nginx:9.99" Warning Failed 6s (x2 over 18s) kubelet Failed to pull image "nginx:9.99": … docker.io/library/nginx:9.99: not found Warning Failed 6s (x2 over 18s) kubelet Error: ErrImagePull Normal BackOff 4s (x2 over 16s) kubelet Back-off pulling image "nginx:9.99" ```
Registry's answer in the eventCause
…: not found / manifest unknownThe repository exists but the tag does not: a typo, or the image was never pushed.
pull access denied, repository does not exist or may require authorizationA typo in the image name, or a private repository without credentials (imagePullSecrets).
401 UnauthorizedPrivate registry; the pull secret is missing or wrong.
ErrImagePull and ImagePullBackOff are one problem ErrImagePull is the failed attempt; ImagePullBackOff is the kubelet waiting before the next attempt, with pauses that grow up to five minutes. The pod alternates between the two. Fixing the image reference fixes both.

🔑 Key takeaways

  • A change to the pod template starts a rollout: a new ReplicaSet grows while the old one shrinks.
  • Old pods are removed only when new ones are Ready, so a release that cannot start stalls safely.
  • kubectl rollout status follows, history lists, undo returns to an earlier template.
  • READY high and UP-TO-DATE low means: stuck rollout, old version still serving.
  • ImagePullBackOff: read the registry's answer in the pod's events; it distinguishes a wrong tag from a wrong name or missing credentials.
